### 🔴🔴 踩到的最隐蔽的坑：部署件上的高置信度是**自证**

→ **部署件上的置信度对新图毫无参考价值**。必须用**折外**模型标定。

### 拒答阈值实测标定（0.60 → **0.90**）
```

错误(n=6)    最高概率 mean 0.6910 median 0.6646 min 0.4919
→ 置信度确实能区分对错（差 0.30）

th=0.60 回答 99.8% 拦下错误 33.3%  ← 会误伤（正确样本最低仅 0.5576）
th=0.90 回答 98.6% 拦下错误 83.3%  回答中正确率 99.95%  ← 采用
th=0.999 回答 78.5% 拦下错误 100%   覆盖率代价太大
```

⚠️ **高置信度也不等于正确**：0.90 下仍有 1/6 错误带着 ≥0.90 溜过去。
⚠️ **只有 6 个错误样本**，统计基础极薄，阈值只能当起点，不是定论。

## 抓到的 4 个 bug

1. 🔴🔴 **LangGraph 静默丢弃 schema 未声明的入参**（最危险）
   `AgentState` 是 `TypedDict(total=False)`，未声明的 `image_paths` **直接消失、不报错**
   → 有图也走文本路径，返回值「看起来都正常」。

2. **多图合并所有 KB 给互斥建议**：3 张不同类别的图 → 12 个 KB / 3 套互斥建议。
   **类别是互斥的诊断结论，不是可并集的信息**。改为只取主类别 + 显式告知冲突。
3. **验收断言写错**：`top_cosine` 两条路径语义不同（文本=真实余弦 0.3355 / 视觉=-1.0），

## P0 既有 bug（用户批准后已真修）

`vector_index.load_fitted_embedder()` 硬编码读 **cause 级**索引路径，
kb 模式下 fitted 在 `faiss_index_kb.tfidf_svd.pkl` → 查询侧拿 `None`
→ 用单条 query 重新 fit 一个迷你 TF-IDF+SVD。

**修法**（P0 冻结区，经用户批准）：

  （两索引 vocab/SVD 基不同，单变量会让一个 mode 复用另一个的 fitted）；
- `_embed_query(..., fitted_path=None)` 缺失即 `ValueError`；
- `HybridRetriever.faiss_path` 透传 2 处调用点。
验收脚本 `patch_offline_embedder()` 旁路**已删**，换`assert_no_bypass_needed()`
**反向自检**（修复被回退直接 AssertionError）。A~F 重跑 **ALL PASS**。

### 🔴 归因两次修正（别照抄旧结论）

原写「→ 抛 `TruncatedSVD n_components` 越界」。实测（`exp/_tmp_bug_mechanism.py`）
有**两条**后果：

| 情形 | 机制 | 表现 | 性质 |
|---|---|---|---|
| (a) query 短，TF-IDF 只切 1 个 token | `n_components=0` | `InvalidParameterError: Got 0` | **吵闹**，原判断对 |
| (b) query 长，切出多个 token | fit 出 **vocab=3** 迷你模型，查 16367 词表索引 | 维度同为 1024 → FAISS**不报错**，静默返回假相似度 | **安静**，危害更大 |

(b) 实测：迷你向量 top1 = KB002 Not Sticking to the Bed cos=0.3613，
正确答案是 KB006 Stringing or Oozing。与 `assert_backend_consistent`
拦的同一类 → `strict=True` 主动报错是必要的。

> **教训**：又是一次「按语义推断 bug 机制」被实测推翻（前一条是映射层
> 「字面对得上≠ 现象对得上」）。`InvalidParameterError` 只在**单词 query** 下出现，
> 稍长 query 根本不报错。**只测一个 case 就下机制结论 = 测得不够。**

### ⚠️ 修好后暴露的独立缺陷（未修，需另立任务）

离线兜底 TF-IDF 对**中文 query 完全失效**：
索引语料是英文（`KB001 text='Not Extruding at Start...'`）+ 默认

## ✅ Zenodo 加速下载：找到 12× 提速方法，DC-04 已从「暂缓」转「下载中」

用户问「Zenodo 有没有别的加速下载方法」。**实测找出了**，不是换工具而是换**IP 池**。

### 根因：Zenodo 有 6 个前置 IPv4，此前只用了 1 个

本机 DNS 被污染，公共 DNS（8.8.8.8 / 1.1.1.1）能查到**6 个可达 IPv4**：
`188.185.48.75` / `188.185.43.153` / `188.184.98.114` / `188.184.103.118` /
`137.138.153.219` / `137.138.52.235`（IPv6 `2001:1458:d00:13::100:f2` 本机不通）
全部返回 **HTTP 206 = 支持 Range 分片**。单IP 速度 46~125 KB/s（差异 2.7 倍），
**跨 IP 可叠加**。

### 实测并发-速度曲线（找拐点，不靠猜）

| 方案 | 合计速度 | 12.6 GB 预计 |
|---|---|---|
| 单 IP 单连接（历史做法） | 41 KB/s | **85 h** |
| 6 IP × 1 = 6 并发 | 245 KB/s | 14 h |
| **6 IP × 3 = 18 并发** | **500 KB/s** | **7.0 h** ← 默认 |
| 6 IP × 6 = 36 并发 | 587 KB/s | 6.0 h |

→ **拐点在 18~36 之间**，18 已拿 85% 收益，36 只再快 17% → **加速 12×**。

### 交付 `scripts/fetch_zenodo_dc04.py`（已在后台跑，约 7 h）

- 6 IP × 3 连接= 18 并发，分片号 mod 6 分配 IP
- **断点续传按磁盘实际文件大小判定，不信 json**（同「别信元数据」纪律）
- 每片重试 5 次 + 指数退避；下完自动拼接 + **三重结构化校验**
  （大小 / zip 条目数 / `testzip()` CRC / 顶层目录分布）

## 续传崩溃 2 次（均已修），限流已自行解除

第二次跑（21:20→ 次日 02:34，5h28m）推进到 **2,832/3,012 = 94%**，
末尾几百片撞上**第二次限流**（日志里成片 `curl rc=7` = Failed to connect），
然后脚本自己崩了。

### ③除零崩溃：把「限流」这个关键信息带走了（已修）

```python
rate = gotb / el if el > 0 else 0          # el 兜底了，rate 没兜底
eta = (...).getb / rate / 3600              # rate=0 → ZeroDivisionError
```
限流时首批分片全失败 → `gotb=0` → `rate=0` → 崩。
**致命之处**：一崩就只剩 traceback，「正在被限流」这个最重要的现场信息没了，
看起来像程序 bug，而不是网络被限流。

修法：`rate > 0` 才算 eta，否则显示 `-- 限流/无数据 --`，
**且不中断循环**（`as_completed` 跑完如实汇报成功/失败片数）。
顺带把 `failed` 计数打出来，别再「静默失败」。

### ④ rc=7 是第二阶段的限流形态

早上限流表现为**降速**（46→4 KB/s，rc=0），深夜这轮表现为**直接连不上**
（rc=7 Failed to connect）。同一件事的两种表现，别当成两个问题。

### 恢复：限流会自行解除，降到 6 并发即可

02:34 后复测 rc=0 恢复；用 `--per-ip 1`（6 并发）续传，
**110 秒完成 15 片**（≈ 550 KB/s），远好于18 并发被限流时的 0。
→ **降并发反而更快**，因为不再触发限流。这才是正确取舍。

**教训：并发不是越高越好，要看服务端是否限流。**
「18 并发 500 KB/s」是短时峰值；稳态下**6 并发不触发限流、净收益更高**。
